# Module 2: Multi-Provider LLM Abstraction + BYO Retrieval

## Context

Module 1 is complete with a working chat app using OpenAI's Chat Completions API directly. The codebase currently:
- Uses `AsyncOpenAI` client with hardcoded `gpt-4o-mini` model
- Has `openai_api_key` as the only LLM config
- Stores messages with unused `metadata jsonb` column ready for model tracking
- Has `openai_thread_id` column in threads (unused, from Responses API design)

**Goal**: Transition to a provider-agnostic abstraction that supports:
- OpenAI (direct)
- OpenRouter (multi-model routing)
- Ollama (local models)
- LM Studio (local models)
- Any OpenAI-compatible endpoint

**Architectural Decision**: Option A (Replace) - Remove OpenAI-specific patterns, single Chat Completions pattern going forward.

**Complexity: ⚠️ Medium** - Config refactoring with multiple touch points, but all providers use identical SDK interface.

---

## Architecture Overview

All supported providers implement the OpenAI Chat Completions API. The abstraction is simply:
- Different `base_url` per provider
- Different `api_key` (or empty for local)
- Different model name formats
- Optional provider-specific headers (OpenRouter)

Single `AsyncOpenAI` client configured at startup based on environment variables.

### Provider Configurations

| Provider | Base URL | API Key Required | Model Format | Extra Headers |
|----------|----------|------------------|--------------|---------------|
| OpenAI | (SDK default) | Yes | `gpt-4o-mini` | None |
| OpenRouter | `https://openrouter.ai/api/v1` | Yes | `openai/gpt-4o-mini`, `anthropic/claude-3.5-sonnet` | `HTTP-Referer` |
| Ollama | `http://localhost:11434/v1` | No | `llama3.2`, `mistral` | None |
| LM Studio | `http://localhost:1234/v1` | No | Model name from UI | None |
| Custom | User-defined | User-defined | User-defined | None |

These three tasks have no dependencies and can be executed simultaneously.

**1.1 Update `backend/app/config.py`**

Add provider enum and new settings:

```python
from enum import Enum
from typing import Optional

class LLMProvider(str, Enum):
    OPENAI = "openai"
    OPENROUTER = "openrouter"  
    OLLAMA = "ollama"
    LM_STUDIO = "lm_studio"
    CUSTOM = "custom"

PROVIDER_PRESETS = {
    LLMProvider.OPENAI: {
        "base_url": None,
        "default_model": "gpt-4o-mini",
        "requires_key": True,
    },
    LLMProvider.OPENROUTER: {
        "base_url": "https://openrouter.ai/api/v1",
        "default_model": "openai/gpt-4o-mini",
        "requires_key": True,
    },
    LLMProvider.OLLAMA: {
        "base_url": "http://localhost:11434/v1",
        "default_model": "llama3.2",
        "requires_key": False,
    },
    LLMProvider.LM_STUDIO: {
        "base_url": "http://localhost:1234/v1",
        "default_model": "local-model",
        "requires_key": False,
    },
}
```

New settings fields:
- `llm_provider: LLMProvider = LLMProvider.OPENAI`
- `llm_api_key: str = ""` (replaces `openai_api_key`)
- `llm_model: Optional[str] = None` (override default)
- `llm_base_url: Optional[str] = None` (for custom endpoints)
- `openrouter_app_name: str = "Claude RAG"` (for HTTP-Referer header)

Keep `openai_api_key` temporarily for backward compatibility.

## Key Design Decisions

1. **Single client at startup** - Simpler than per-request factory, sufficient for most use cases
2. **Provider presets + custom override** - Convenience for known providers, flexibility for custom
3. **LangSmith `wrap_openai()` works with custom base_url** - Research confirms this works
4. **Metadata in existing column** - No schema changes needed for message tracking
5. **Backward compatible** - `openai_api_key` still works during transition
